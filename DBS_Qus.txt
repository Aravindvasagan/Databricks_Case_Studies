1. Core Join Strategies
These define how Spark moves and merges data across the cluster. 

Broadcast Hash Join (BHJ):
How it works: The smaller table is copied entirely to every executor node.
Performance: The fastest join as it avoids an expensive "shuffle".
Recommendation: Best for small tables (default threshold is 10MB, but often tuned up to 200MB-500MB).
Use Case: Joining a massive sales_fact table with a small product_dimension table.
Broadcast Hash Join (BHJ)
The Concept: Spark sends a copy of the small table to every worker node so the large table doesn't have to move.
Performance: Fastest; zero shuffling of the large dataset.
Real-time Use Case: Mapping country codes in a massive transaction table.
python
from pyspark.sql.functions import broadcast

# Large Table (Fact): sales_df (1 Billion rows)
# Small Table (Dimension): countries_df (200 rows)
# Optimization: Force broadcast of the tiny table
result = sales_df.join(broadcast(countries_df), "country_id")
-----
Sort-Merge Join (SMJ): default
How it works: Both datasets are shuffled by the join key, sorted locally, and then merged.
Performance: Robust for very large datasets as it can spill to disk if memory is low.
Recommendation: Default for large-to-large equi-joins.
Use Case: Joining two massive tables like web_logs and user_transactions.
------
6. Dealing with Data Skew (The "Salt" Optimization)
The Concept: If one city_id (like 'London') has 90% of the data, that worker node will be slow. We "salt" the key by adding a random number to break the big chunk into smaller ones.
Real-time Use Case: Processing high-traffic events where a few keys dominate.
python
# 1. Add a random salt to the left table
from pyspark.sql.functions import rand, concat, lit
skewed_df = df_left.withColumn("salt", (rand() * 10).cast("int"))
skewed_df = skewed_df.withColumn("salted_key", concat("city_id", lit("_"), "salt"))

# 2. Explode the right table to match all possible salt values
# (This ensures the join still finds the match)

Pro-Tip: If you see one task in your Spark UI taking 10x longer than others, you have Data Skew. Use the Skew Join Hint in Databricks:
python
# Databricks specific hint for AQE
result = df1.hint("skew", "city_id").join(df2, "city_id")
------
Shuffle Hash Join (SHJ):
How it works: Shuffles both datasets but only builds a hash table for the smaller side in each partition.
Performance: Faster than SMJ because it skips the sorting phase, but riskier as it may cause Out-Of-Memory (OOM) errors if one partition is too big.
Use Case: Medium-sized tables where data is evenly distributed and can fit into memory.

Broadcast Nested Loop Join (BNLJ):
How it works: Broadcasts one table and uses a nested loop to evaluate conditions.
Performance: Very slow; typically a fallback.
Use Case: Mandatory for Non-Equi Joins (joining on >, <, or !=) when one table is small. 

2. Filtering Join Types (Semi & Anti) faster than inner and Performance: Extremely efficient for "Not In" or "Except" logic.
These are used for filtering rather than data enrichment. 
Join Type 	Result	Real-Time Use Case
Left Semi	Rows in the left table that have a match in the right.	Filtering: "Show me only customers who made a purchase today."
Left Anti	Rows in the left table that have no match in the right.	Exception Finding: "Find customers who haven't updated their profiles in 6 months."
3. Performance Optimization Recommendations
To ensure your joins run efficiently, follow these best practices:
Enable Adaptive Query Execution (AQE): Databricks recommends keeping AQE enabled. It can dynamically switch a slow Sort-Merge Join to a fast Broadcast Join at runtime if it detects the data is smaller than expected.
Manually Broadcast: If Spark doesn't automatically broadcast a table you know is small, force it using a hint: df1.join(broadcast(df2), "id").
Handle Data Skew: Skewed data (where one key has millions of rows and others have few) causes specific nodes to lag. Use Databricks' Skew Join Optimization or manually "salt" the keys to distribute the load.
Analyze Your Tables: Regularly run ANALYZE TABLE table_name COMPUTE STATISTICS to help the Cost-Based Optimizer (CBO) make the right join strategy choice.
Use Photon Engine: On Databricks, enabling the Photon engine provides vectorized execution, which significantly accelerates join operations by default.

remove the dublicate in diffrent ways in dataframe

1.dropDuplicates() (Most Common)
This is the standard programmatic way to handle duplicates.
Whole Row: Removes rows where every single column is identical.
Specific Columns: Only looks at the columns you list (useful for keeping only one entry per ID).
df = df.dropDuplicates()
df= df.dropDuplicates(["id"])

2. distinct()
This is simpler but less flexible. It always compares the entire row. It is essentially a shorthand for dropDuplicates() without arguments.
df = df.distinct()

3. Window Functions (row_number)
Use this when you have duplicates but want to choose which one to keep (e.g., keep the "latest" record based on a timestamp).
Wn = df.withColumn('rn',row_number().over(Window.partitionBy("customers_id").orderBy(desc("timestamp"))))
df = wn.filter('rn==1').drop(rn)

4. Spark SQL DISTINCT or GROUP BY
If you prefer writing SQL logic, you can use the GROUP BY approach which gives you control over aggregating the other columns.
-- Method A: Simple distinct
SELECT DISTINCT * FROM my_table

-- Method B: Group by with aggregation (e.g., get the max price for each product)
SELECT product_id, MAX(price), MIN(date)
FROM my_table
GROUP BY product_id

Performance Tip: dropDuplicates vs Window
Use dropDuplicates for simple cleanup. It is highly optimized in Spark.
Use Window only if you need to pick a specific record (like the most recent one). It is more "expensive" because it requires more complex sorting.

 Common Transformations (Lazy)
Transformations create a new DataFrame from an existing one.  
select(): Projects a set of expressions (e.g., df.select("name", "age")).
filter() / where(): Filters rows based on a condition.  
withColumn(): Adds a new column or replaces an existing one.  
withColumnRenamed(): Renames an existing column. ->df.groupBy(name).sum(sal).withColumnRenamed(sum(sal)), total_sum) 
				more than one column in groub by using agg()->df.groupBy(name).agg(sum(sal),count(name).alias(cn_name)).withColumnRenamed(sum(sal)), total_sum) 
drop(): Removes specific columns.
groupBy(): Groups the DataFrame using the specified columns for aggregation.  
join(): Joins with another DataFrame (e.g., inner, left, outer).
orderBy() / sort(): Returns a new DataFrame sorted by the specified columns.  
distinct() / dropDuplicates(): Removes duplicate rows.
 
 0---- actions----on dataframe----
 Actions trigger the computation and return results.  
 show(n): Displays the first $n$ rows in a tabular format (default is 20).
 display(): A Databricks-specific function that creates a rich, interactive table and chart view.
 count(): Returns the number of rows.  
 collect(): Returns all records to the driver as a List of Rows. Warning: High risk of OutOfMemory errors for large datasets.
 take(n): Returns the first $n$ rows.  
 first(): Returns the very first row.  write: Saves the DataFrame to a data source (e.g., df.write.format("delta").save(path)).
--------- rdd
Narrow Transformations
map(func): Passes each element through a function.  
filter(func): Returns a new RDD with elements that satisfy a condition.  
flatMap(func): Similar to map, but each input item can be mapped to 0 or more output items (flattens the result).  
union(dataset): Combines two RDDs.

Wide Transformations
groupByKey(): Groups values for each key in the dataset.  
reduceByKey(func): Merges the values for each key using an associative reduce function. (More efficient than groupByKey because it combines data before shuffling).  
join(otherDataset): Joins two RDDs based on a common key.  
distinct(): Returns a new RDD containing only unique elements.

groupByKey() vs reduceByKey(func) in rdd
If the interviewer asks about groupBy in RDDs, mention that reduceByKey is almost always better. groupByKey shuffles all data first, which can cause "Out of Memory" errors. reduceByKey combines data locally on each executor before shuffling, which is much more efficient.

?Wordcount from the file ->total words and particular word into count, all words in uniq counts.

# Sample data simulating lines from a file
data = ["apple banana apple", "orange apple banana", "banana grape"]

# Create RDD
rdd = sc.parallelize(data)

# Flatten lines into words
words_rdd = rdd.flatMap(lambda line: line.split(" "))

# 1. Total Word Count
total_words = words_rdd.count()

# 2. Particular Word Count (e.g., 'apple')
target_word = "apple"
particular_count = words_rdd.filter(lambda word: word == target_word).count()

# 3. All Unique Word Counts (Classic WordCount)
word_counts_rdd = words_rdd.map(lambda word: (word, 1)) \
                           .reduceByKey(lambda a, b: a + b)

# Collect results to driver
unique_counts = word_counts_rdd.collect()

print(f"Total Words: {total_words}")
print(f"Count of '{target_word}': {particular_count}")
print(f"Unique Word Counts: {unique_counts}")
